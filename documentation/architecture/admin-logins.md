# WPB-13: Track admin logins (1.3.0)

Story, owner decisions 1-7 and AC 1-15: `documentation/backlog.md` § WPB-13. Security guidance: `documentation/security/wpb-13-admin-logins.md` (SB13-01..15, decisions at the end).

Summary. Every successful admin login becomes one row in the existing `{prefix}bouncer_log`. The row has action `login` and rule `admin_login`, and its own allowance in the write budget. Application-password and XML-RPC logins are de-duplicated per hour. Each admin has a short per-site location history in user meta (IP range + country, 90 days sliding, up to 20 entries). A login from a range or country not in that history queues one email through the existing `AlertNotifier`. **No schema change**: `Installer::DB_VERSION` stays `3`. Rows are matched to a user by a fixed `User ID N:` prefix in `reason`, which only this feature writes (see Privacy).

## 1. Classes (new namespace `WPBouncer\AdminLogins\`, folder `src/AdminLogins/`)

| Class | Layer | Responsibility |
|---|---|---|
| `LocationHistory` | Decision core (pure, immutable) | The per-user history. `static from_meta( mixed $raw ): ?self` returns `null` for absent or invalid data, meaning "never recorded". `to_meta(): array`. `entries(): list<array{r:string,c:string,t:int}>`. `since(): int`. `has_range( string )`, `known_countries(): string[]`. `with_login( string $range, string $country, int $now, int $window, int $max ): self` prunes entries older than `$now - $window`, refreshes or adds the range (`t = now`, and `c` overwritten only by a non-empty country), then drops the oldest beyond `$max`. `pruned( int $now, int $window ): self`. |
| `LoginLocationPolicy` | Decision core (pure) | `__construct( int $window_seconds = 90 * DAY, int $max_entries = 20 )`. `static range_of( string $ip ): string` gives `a.b.c.0/24` for IPv4 (IPv4-mapped IPv6 is unmapped first via `IpUtils::canonical()`), the `/64` network in `inet_ntop` form plus `/64` for IPv6, and `''` for an invalid IP. `assess( ?LocationHistory $h, string $range, string $country, int $now ): LoginAssessment`. Rules below. The per-user hourly cap (3) lives in `AlertNotifier`, not here (CR-3: `should_alert()` was removed). |
| `LoginAssessment` | Decision core (pure value) | Read-only: `first` (no history existed), `new_range`, `new_country`, `history` (the updated `LocationHistory` to save). `is_new_location(): bool` is `! first && ( new_range \|\| new_country )`. |
| `LoginEvent` | Decision core (pure value) | `user_id`, `login`, `ip`, `range`, `country`, `method`, `time`. The constructor strips control characters from the login and caps it at 60 characters. `method` must be one of the `METHOD_*` constants (§3), otherwise `\InvalidArgumentException`. `static reason_prefix( int $user_id ): string` returns `"User ID {$id}:"`. `reason( string $note ): string` builds the row text (§4). `email_detail( LoginAssessment ): string`. `to_array(): array` is the shape passed to hooks. |
| `LoginHistoryRepository` | Storage adapter | `load( int $user_id ): ?LocationHistory` via `get_user_option( self::META, $id )`. `save( int $user_id, LocationHistory )` via `update_user_option( $id, self::META, $h->to_meta() )`. `delete( int $user_id )` via `delete_user_option()`. `prune_expired( int $window, int $batch = 200 ): void` for cron. `const META = 'wpb_login_seen'`; the stored key is `{blog_prefix}wpb_login_seen` (per site, see Multisite). |
| `AdminLoginRecorder` | Integration | Registers the hooks, gathers facts from WordPress and `Plugin`, writes the row, asks `AlertNotifier` to queue the mail, saves the history and fires the actions. `const LOG_RULE = 'admin_login'`. Its only state is per request: `$recorded` (user IDs already handled) and `$xmlrpc_auth` (user IDs that passed `authenticate` on XML-RPC). |
| `Privacy\AdminLoginPrivacy` | Integration | Exporter and eraser for login rows and history (§8). |

`Admin scope` (decision 1) is a private method of the recorder, because it needs WordPress: `is_super_admin( $user->ID ) || in_array( 'administrator', (array) $user->roles, true ) || $user->has_cap( 'manage_options' )`, then filtered by `wp_bouncer_admin_login_is_admin`. It is evaluated on the `WP_User` that the hook passes, at login time (AC 3). **Never** call `current_user_can()`, `wp_get_current_user()` or `is_user_logged_in()` inside the application-password hook: it runs inside `determine_current_user` and would recurse.

## 2. Decision rules (`LoginLocationPolicy`)
- `first` is true when `$h === null` (meta absent or unreadable). The login then builds history silently (AC 7, SB13-13).
- An expired history is **not** first. The meta keeps `since` and an empty entry list after pruning, so a dormant admin account used again after 90 days alerts. AC 14 "expired history" therefore expects an alert. This closes the "dormant admin account" evasion.
- `new_range` is `$range !== '' && ! $h->has_range( $range )`, after pruning.
- `new_country` is `$country !== '' && known_countries !== [] && ! in_array( $country, known_countries )`. While the history holds no country (no geo database until now), a country is learned silently and the range decides alone. Installing a geo database therefore does not alert every admin at once.
- The email decision is `AlertNotifier::check_admin_login()`: new location, reliable IP (the recorder only assesses then) and at most 3 per user and hour. Over the cap the alert is "throttled": counted in the login throttle notice (RT-03).
- Unreliable IP (see §5): no assessment, the history is neither read nor written, no alert.

## 3. Hooks consumed (all in `AdminLoginRecorder::register()`)
`register()` only calls `add_action`/`add_filter`. It reads no option and runs no query. `Plugin::register()` calls `( new AdminLoginRecorder( $this ) )->register()` next to `alerts()->register()`, **outside** the `is_disabled()` branch, because recording never refuses anyone (same reasoning as alerts). Nothing is added to `plugins_loaded`.

| Hook | Priority / args | Method constant (row label) |
|---|---|---|
| `wp_login` | 20, 2 (`$login`, `WP_User`) | `METHOD_INTERACTIVE` "interactive password" |
| `application_password_did_authenticate` | 20, 2 (`WP_User`, `$item`; `$item` is ignored, its name is never stored) | `METHOD_APP_REST` "application password (REST)" or `METHOD_APP_XMLRPC` "application password (XML-RPC)" (XML-RPC when `XMLRPC_REQUEST` or `current_request()->is_xmlrpc()`) |
| `two_factor_user_authenticated` (Two Factor plugin) | 20, 1 | `METHOD_INTERACTIVE_2FA` "interactive password + two-factor" |
| `wp_bouncer_record_admin_login` (ours, for other 2FA plugins) | 10, 1 (`WP_User`) | `METHOD_INTERACTIVE_2FA` |
| XML-RPC only (registered only when `defined( 'XMLRPC_REQUEST' ) && XMLRPC_REQUEST` at boot): `authenticate` at `PHP_INT_MAX` (1 arg, notes the ID of a returned `WP_User` in `$xmlrpc_auth`, returns the value unchanged), and `xmlrpc_call` (20, 0 args) | | `METHOD_XMLRPC_PASSWORD` "password (XML-RPC)". Recorded when `get_current_user_id()` is in `$xmlrpc_auth` and not already in `$recorded` (application-password logins mark the user first). Covers a stolen admin password used over XML-RPC, which fires no `wp_login`. |

Priority 20 runs after the existing priority -1 release callbacks. The Two Factor plugin ends the request at `wp_login` priority 10 for users with 2FA, so the first factor alone writes nothing, and the login is recorded when the second factor passes (SB13-06b). Other 2FA plugins that exit at `wp_login` should return true from the new filter `wp_bouncer_admin_login_defer( bool $defer, WP_User, string $method )` (default: true only when the user uses Two Factor **and** `Two_Factor_Core::wp_login` is hooked to `wp_login` after priority 20; the real one exits at 10, so reaching our priority 20 means no challenge happened, e.g. single sign-on or a magic link, RT-09) and then fire `wp_bouncer_record_admin_login` once the second factor passes. A deferred password step records nothing and saves no history (RT-06). Until they do, those logins are a documented gap. **Verify in an integration test** that the Two Factor plugin fires `two_factor_user_authenticated` after a successful second factor. If the installed version doesn't, record that as a known gap in the docs.

## 4. Recording flow (`AdminLoginRecorder::handle( WP_User $user, string $method )`)
The whole body runs in `try { … } catch ( \Throwable $e )`. On error it calls `error_log( 'WP Bouncer: admin login not recorded: ' . get_class( $e ) . ': ' . $e->getMessage() )` only when `WP_DEBUG_LOG` is set. It never returns a value, never calls `wp_die`, and never rethrows (AC 11, SB13-01). Third-party listeners on our actions run inside the same try.

1. Return unless `alerts.record_admin_logins` is on (decision 7).
2. Return unless the user is an admin (§1).
3. Set an in-progress guard for the user ID first, before any filter runs (RT-04). Return if the user ID is already in `$recorded`; otherwise add it (one row per user and request). On multisite, steps 1 and 2 are checked per candidate site (§9).
4. `$ip = plugin->client_ip()` (never a header read, SB13-02) and `$range = LoginLocationPolicy::range_of( $ip )`.
5. **Dedupe, for non-interactive methods only** (application passwords and XML-RPC password, SB13-08). On a network the check runs first, before any site is listed or switched, against a site transient shared by all sites (RT-10); the key is set only after a recording succeeded, not before (CR2-6). On a single site it is the store. Key `'login_seen:' . $user_id . '|' . $range . '|' . $method` (plus `'|b' . $origin_blog_id` for a super admin on a network: they are recorded only on the origin site, so a login on site 2 must not hide one on site 1 (RT-14); site admins keep a network-wide key that ends in a short hash of the sorted sites their capabilities meta lists, read before any `get_site()` or switch, plus `'|b' . $origin_blog_id` when the origin is not in that list, so a site granted within the hour is not hidden (RT-17)) in `plugin->store()` (the store hashes it to `wpb_<md5>`, so no raw IP is kept). If the key exists, return: a single store read, no geo lookup, no meta read. Otherwise it is set for an hour after the first successful write. The first login from a new range always has a new key, so it writes and is assessed.
6. `$country = '' !== $ip ? plugin->geo()->lookup( $ip ) : ''`.
7. `$reliable = plugin->client_ip_is_reliable()` (new public method: `'' !== ip && IpUtils::is_valid( ip ) && '' === ip_resolver()->rejected_subject( $server ) && client_can_be_banned()`). It is false for loopback, trusted-proxy addresses and a header IP source with no trusted proxies.
8. If reliable: `$a = policy->assess( repo->load( $id ), $range, $country, time() )`.
9. Write the row through `plugin->log_writer()->record()` with: `ip`, `country`, `rule` `admin_login`, `action` `login`, `reason` = `LoginEvent::reason( note )`, plus `method`, `uri` and `user_agent` from `current_request()`. `reason` formats (English, like every stored reason; at most 255 characters, and the prefix is at position 0 so truncation never cuts it):
   - `User ID 12: jim — interactive password`
   - `User ID 12: jim — application password (REST) — new location: IP range 203.0.113.0/24, country DE`
   - `User ID 12: jim — interactive password — first recorded login, location history started`
   - `User ID 12: jim — password (XML-RPC) — location not checked: client IP not reliable (check the IP source setting)`
10. If reliable and the login is a new location, ask `alerts()->check_admin_login()` for the decision (`send`, `throttled` or `none`) before the row is written; `throttled` adds " — alert throttled" to the row (RT-03). The row is written with that note. If the decision throws (a failing alert filter), it fails open: `send` (CR2-4).
11. If reliable, `repo->save( $id, $a->history )`, **before** the alert is queued (CR-2; the history is never lost to a queueing failure), and only from these post-authentication hooks (SB13-06b).
11a. If reliable and a new location, call `alerts()->on_admin_login( $event, $a, $row_id > 0, $decision )` (§6). `logged` is false when the budget dropped the login row, so the alert row is written instead (RT-05). A throttled decision queues a capped event that is counted in the login throttle notice and never mailed.
12. `do_action( 'wp_bouncer_admin_login_recorded', $event->to_array(), array( 'first' => …, 'new_range' => …, 'new_country' => …, 'reliable' => … ) )`.

Allowlisted IPs and monitor mode follow the same flow. They write the row and history and can alert (SB13-06d). A site that wants silence for known ranges uses the filter in §7.

## 5. Write budget (SB13-09)
`WriteBudget` gains a third allowance, the **login lane**:
- Constructor: `__construct( CounterStoreInterface $store, Clock $clock, int $per_minute, int $priority_per_minute = 30, int $login_per_minute = 20 )`, with `max( 5, … )`.
- `public const LANE_NORMAL = ''`, `LANE_PRIORITY = 'p'`, `LANE_LOGIN = 'l'`. `public static function lane( array $entry ): string` returns `LANE_LOGIN` for `action === ACTION_LOGIN`, `LANE_PRIORITY` when `is_priority()`, and `LANE_NORMAL` otherwise. `consume_lane( string $rule, string $lane ): bool`. The existing `consume( $rule, bool $priority )` and `peek()` keep their signatures and delegate, so `Firewall` and `UploadsGuard` don't change. Counter keys are `log_budget:` / `log_budget_p:` / `log_budget_l:` plus the minute.
- `BudgetedBlockLog::record()` uses `consume_lane( $rule, WriteBudget::lane( $entry ) )`. Only `ACTION_ALERT` still bypasses the budget. Login rows dropped over budget are counted under `admin_login` in the existing `suppressed` summary.
- `Plugin::write_budget()` adds the filter `wp_bouncer_log_login_budget_per_minute` (default 20, at least 5).
- `BlockLogInterface` gains `public const ACTION_LOGIN = 'login';` ("Not a block: a successful administrator login").

## 6. Alert (`AlertNotifier`)
- New public `on_admin_login( LoginEvent $e, LoginAssessment $a ): bool` (returns whether the alert was queued):
  1. Return false unless `wants( 'admin_login_location' )` (needs `alerts.enabled` too).
  2. Return false if `! apply_filters( 'wp_bouncer_admin_login_alert', true, $e->to_array(), $a_flags )`.
  3. Per-user throttle: `store()->increment( 'login_alert:' . $user_id, HOUR_IN_SECONDS )`. Return false when the result exceeds 3.
  4. `queue( 'login', 'Administrator login from a new location', $e->email_detail( $a ), 'login|' . $id, '', false, true /* logged: the login row is the record */, array(), array( 'ctx' => array( 'actor' => "{$login} (user ID {$id})" ) ) )`.
- `email_detail` reads: `User: jim (user ID 12). Method: application password (REST). New: IP range 203.0.113.0/24, country DE.` It has no email address, password, token or application-password name (AC 9, SB13-03). IP, country, time and browser come from `context()` as usual, so they are this request's values, and `AlertFormatter::clean()` strips control characters.
- `flush()` gets a fourth bucket, `login`: `MAX_LOGIN_PER_HOUR = 10`, `THROTTLE_KEY_LOGIN = 'wpb_alert_count_login'`. The bucket test becomes settings, then `'login' === type`, then critical, then general. Login mail never uses the critical budget for new administrators. Login events over the cap go into `$dropped` exactly like settings events. They produce one "Admin login alerts throttled: N not emailed, see the Activity Log" notice per site and hour, keyed `wpb_alert_login_notice`. To do this, generalise `$dropped` and the notice to per bucket (`settings`, `login`).
- `AlertFormatter::format()`: a mail where every event is `login` gets the closing text "If this was you, there is nothing to do. If not, change this account's password, revoke its application passwords and log out its other sessions (Users → Profile), then check the Activity Log." With mixed events, the subject suffix is "including an administrator login from a new location" when no admin event is present.
- `wants()`'s doc comment lists the new kinds.

## 7. Settings, UI and public hooks
**Settings keys** (both go in `settings['alerts']`, both default `true`; `Settings::defaults()`, `sanitize()` via `self::bool()`. The existing merge gives upgraded sites `true`, which satisfies AC 8):
- `alerts.record_admin_logins`: "Record administrator logins in the Activity Log". Turning it off stops rows, history and the alert (decision 7). It does **not** depend on `alerts.enabled`.
- `alerts.admin_login_location`: the email. It needs `alerts.enabled` and `record_admin_logins`.

They live under `alerts.*`, so `SettingsDiff::is_risky()` already treats switching either one from on to off as risky (it's emailed and audited), and `silences_alerts()` keeps that alert uncapped. This is wanted: an attacker would turn these off first. No `SettingsDiff` code change, only a test.

**General tab** (`views/general.php`, `#wpb-alerts`): one new indented checkbox in "Email me when:" reading "an administrator logs in from a new location (a country or network not seen for that account in the last N days)", N = `AdminLoginRecorder::window_days()`. It also gets a new row, "Administrator logins", with the recording checkbox and help text. The help text says that turning recording off also stops the new-location email; that application-password and XML-RPC logins are recorded once per hour per network; and that with no geo database only the network is compared. When `'remote_addr' !== ip_source && [] === trusted_proxies`, the row also shows "Location checks are skipped until a trusted proxy is configured" (SB13-02). Update the "At most 20 emails" sentence to mention the separate limit of 10 login alerts.

**Activity Log** (AC 6): add `ACTION_LOGIN` to the filter list in `LogListTable` (line ~158). `AdminController::action_label()` returns `__( 'Admin login', 'wp-bouncer' )`. `log_rule_labels()` adds `admin_login => __( 'Admin logins', 'wp-bouncer' )`. The badge class `wpb-badge-login` uses a neutral style, and the text label carries the meaning, not colour. Output is already escaped (`esc_html`), and the CSV export already goes through `CsvSanitizer`.

**Threat counts** (AC 5, SB13-10): `BlockLog` gains `public const NON_THREAT_ACTIONS = array( 'alert', 'login' )`. `top()` and `per_day()` change `action <> 'alert'` to `action NOT IN (%s, %s)` with bound values. `WIDGET_ACTIONS` and `recent()` are allow-lists and are unchanged. WPB-11 must count only `blocked`, `monitored` and `lockout` (allow-list), and its design must reference this constant.

**Public hooks (new)**
| Hook | Type | Args | Purpose |

## 8. Privacy (decision 6, AC 13, SB13-10/11)
- **Row matching without a schema change.** Login rows are matched by `rule = 'admin_login' AND action = 'login' AND reason LIKE <esc_like( 'User ID 12:' )>%`, bound with `$wpdb->prepare()`. This is reliable because only `AdminLoginRecorder` writes `admin_login` rows, and the prefix is at position 0 with a `:` delimiter, so ID 1 never matches ID 12 and a login name containing "User ID 5:" can't match another user. The `rule` index narrows the scan. `LIKE` with a literal prefix behaves the same on MySQL, MariaDB and SQLite. A `user_id` column was declined: the owner decided against it on 2026-10-23, it would need a migration on large logs, and the prefix match is exact. **`DB_VERSION` is not bumped.**
- **Exporter** `wp-bouncer-admin-logins` ("Site security: administrator logins"). Page 1 exports the history entries (IP range, country, last seen UTC, and "history kept since"). It then exports the login rows (time UTC, IP, country, method parsed from reason, browser) with keyset paging by `id`, 500 per page, following the `export_traffic` pattern.
- **Eraser** `wp-bouncer-admin-logins`. On each page it selects up to 500 matching ids, then runs `DELETE … WHERE id IN (%d,…)` (no `DELETE … LIMIT`, which SQLite builds may lack). It replaces the history with a tombstone (`{since: now, e: []}`) when one exists, so the next login from a new range still alerts (RT-02), writes an Activity Log alert row "Administrator login data erased for user ID N" on page 1, and reports `items_removed` and `done` when fewer than 500 are found. Rows are **deleted**, not redacted (decision 6). The existing `erase_log` (redaction of `alerts` and `login_lockout` rows) never selects `admin_login` rows and is unchanged. Its audit row "Personal data erased for user ID N" still records the erasure. The audit row is written for every erase request, even when there is nothing to erase. The dedupe check is not atomic, so parallel requests can rarely give a duplicate row (accepted). Throttle and dedupe keys are hashed, expire within an hour and are not erased.
- **Retention**: rows follow `log_retention_days`. History entries are pruned at each login and by `LoginHistoryRepository::prune_expired()` from `daily_maintenance()` and from `maybe_purge()` (the cron-less fallback, SB13-15). That runs in batches of 200 users and at most 1,000 per run, by `umeta_id` cursor on `meta_key = {blog_prefix}wpb_login_seen`. A history whose entries are all expired keeps only `since`.
- **Policy text** (`PrivacyTools::policy_html()`), shown when `record_admin_logins` is on: "When an administrator logs in, we record the account's username and user ID, the IP address, approximate country, browser, time and login method, kept for %d days. To spot logins from unusual places we keep, for each administrator, the network ranges (not full addresses) and countries used in the last N days" (N = `window_days()`, CR-4). Core then flags the changed suggested text on the Privacy screen.
- Deleting a user removes their meta (core); on a single site `delete_user` and, on a network, `wpmu_delete_user` also drop the history key explicitly (CR-5). On a network `delete_user` and `remove_user_from_blog` replace that site's history with a tombstone (only if one existed), so re-adding the account and logging in from a known range still alerts (RT-12). The alert-context actor and the erasure audit row strip control and format characters from the login name like the log rows (`LoginEvent::clean_login()`, RT-07). Their log rows stay until retention, as forensic evidence, so an attacker can't delete the account they used to erase its logins. The privacy eraser is the way to remove them.

## 9. Multisite (AC 4)
- **Revised (RT-01, owner decision, AC 4).** A site administrator's login anywhere on the network is recorded and assessed on every site where they are an administrator: `candidate_sites()` reads the sites from the user's `{base}N_capabilities` meta (not `get_blogs_of_user()`, whose `switch_to_blog()` asks who the current user is mid-authentication), skips deleted, archived and spam sites, and caps the list at `AdminLoginRecorder::MAX_SITES` (100, current site first). `Plugin::run_on_site()` switches the site and swaps the cached settings, log, log writer and write budget, so each site uses its own settings, budget and history. A site is skipped unless the plugin is network-active or in that site's `active_plugins` **and** the site has a saved `wp_bouncer_settings` option (RT-08). Sites whose capabilities meta holds only subscriber, contributor, author or editor are ruled out without switching, ids are de-duplicated (the unprefixed key is site 1), and at most `MAX_SITES` `get_site()` calls are made (RT-10; this pre-filter overrides a `wp_bouncer_admin_login_is_admin` filter that widens scope to those roles on other sites). Each site's recording runs in its own try/catch, so one failure doesn't skip the rest (CR2-3). Application-password and XML-RPC logins noticed inside `determine_current_user` or `authenticate` on a network are queued and recorded at the first safe point after authentication: `rest_pre_dispatch` priority 0, `xmlrpc_call` priority 0 or `wp_loaded`, with `shutdown` priority 0 as fallback, because WordPress's fatal error handler can end the request before `shutdown` fires (RT-15). An XML-RPC application-password login marks the user (`app_auth`) even when the dedupe cache hides it, and `on_xmlrpc_call()` skips marked users, so a deduped call never adds a "password (XML-RPC)" row (RT-16). The flush is idempotent and does nothing during `determine_current_user` or `authenticate`, so no site is switched during authentication (RT-13). The origin site id is stored with the queued login (CR3-1). A fallback alert row for a dropped login row is written to the log of the site the alert is about (RT-11). A super administrator's login is recorded on the site where it happened. IP, country and reliability are resolved once, on the site where the login happened. Alerts for another site are reported as that site, to that site's recipients. The alert caps and notices are counted where the request ran (at `shutdown`).
- Accepted: a role pre-filter skips a core role (e.g. editor) that a site has edited to hold `manage_options`.
- Expected: a site admin can deactivate a non-network-activated WP Bouncer on their own site, which stops recording there.
- Rows go to the log of each such site. Super admins are in scope through `is_super_admin()`.
- History is **per site**: `update_user_option()` stores `{blog_prefix}wpb_login_seen`. That matches the per-site rows, the per-site exporter and eraser (as documented for the existing tools) and per-site uninstall. The tradeoff is that a super admin's first login on each site is silent.
- Single site behaves the same, with key `wp_wpb_login_seen`.

## 10. Uninstall (`uninstall.php`)
- In `wp_bouncer_uninstall_site()`: `delete_metadata( 'user', 0, $wpdb->get_blog_prefix() . 'wpb_login_seen', '', true );`
- Transient regex: `alert_count(?:_critical|_settings|_login)?` and `alert_(?:settings|login)_notice` (replacing `alert_settings_notice`). Dedupe and throttle keys are `wpb_<md5>` and are already covered.
- Rows go with the dropped table.

## 11. Performance (AC 10)
- Non-login requests: zero work beyond `add_action` at boot. XML-RPC hooks are registered only on `xmlrpc.php`.
- Interactive login: a role check, a geo lookup (one indexed query), one meta read, one insert and one meta write. All of this is on a login request, which is already expensive.
- An application-password request by an admin inside the dedupe window: a role check and **one store read**. For a non-admin: a role check only. The "N authentications in the last hour" count is not kept, because it would cost a write per REST call.

## 12. Risks and tradeoffs
- **Sites behind a CDN with IP source "remote_addr"** record the CDN's addresses. The location check sees varying edge ranges, which means noise. `client_ip_is_reliable()` can't detect this. The existing IP-source setup notice is the mitigation, and the help text mentions it.
- 2FA plugins other than Two Factor may end the request at `wp_login` before priority 20, so those logins are not recorded until the plugin fires `wp_bouncer_record_admin_login`. This is documented.
- Login flows that set the auth cookie without `wp_login` (magic links, User Switching) are not recorded.
- History can't catch an attacker who logs in from a range the admin already uses (SB13-06e). The row is the backstop.
- Concurrent logins by one user: the last history write wins. At worst one range is missing, which means one extra alert later.
- Per-user throttle of 3 an hour: the fourth new-location login within an hour is only in the log.

## 16. Data decisions (data-engineer)

No schema change and no `DB_VERSION` bump. Follow the design (§1, §8, §9) except where noted. These answers come from reading the code and the index definitions. I did not run EXPLAIN (the local test DB login failed), so the integration run should confirm the plans.

1. **User meta: confirmed.** Use `get_user_option()` / `update_user_option()` with the per-site key `{blog_prefix}wpb_login_seen`. `usermeta` is never autoloaded and has no size limit that matters at about 1.5 KB. Only administrators ever get a row, so the data is tiny. A network-wide key would contradict the per-site rows, exporter, eraser and uninstall. An option holding all users would be one large autoloaded or locked blob. Save the value as a plain array, never an object.
2. **Prune query: the design's cursor is right, with one change (follow this over §8 "at most 1,000 per run").** Use `SELECT umeta_id, user_id, meta_value FROM {$wpdb->usermeta} WHERE meta_key = %s AND umeta_id > %d ORDER BY umeta_id LIMIT %d`. InnoDB secondary indexes carry the primary key, so `KEY meta_key(191)` is read as an ordered range on `(meta_key, umeta_id)`. The key is shorter than 191 characters, so the prefix index is exact. Match the full key with `=`, never `LIKE`, so `wp_wpb_login_seen` never matches `wp_2_wpb_login_seen`. The result set is one row per administrator who has logged in, which is tens to hundreds. Keep the cursor in an autoload-off option (`wp_bouncer_login_prune_cursor`) and reset it to 0 when a batch returns fewer rows than the limit. Without that, a site with more than 1,000 histories would only ever prune the first 1,000. Write back through `update_user_option()` (not raw SQL) so the user meta cache stays correct. Skip the write when nothing changed. Pruning is only tidiness, because every login also prunes its own user and an expired entry never matches. 1,000 per day is therefore enough.
3. **Eraser and exporter query: the `rule` index is enough, add no index.** `rule = %s` narrows to `admin_login` rows only, which this feature alone writes. Then `action` and `reason LIKE 'User ID N:%'` filter within that set. Add `ORDER BY id LIMIT 500`, which comes straight from the `rule` index because `id` is part of it, and `AND id > %d` for the exporter's keyset. Volume is admins times logins: interactive logins are rare, and app-password and XML-RPC rows are at most 24 an hour per admin, range and method. A realistic site has tens of thousands of rows at 365 days, and even 1M rows is a sub-second scan for a rare, admin-triggered eraser. The login lane (20 rows a minute) caps the worst case. An index on `action` has too few distinct values to help. A `(rule, reason)` index would need a migration for no real gain. If a site ever shows slow erasure, WPB-11's `user_id` column is the answer, not an index.
4. **Select ids, then `DELETE ... WHERE id IN (%d, ...)`: confirmed on all three engines.** Select up to 500 ids, `array_map( 'intval' )`, build the placeholders with `implode( ',', array_fill( 0, count( $ids ), '%d' ) )` and pass the ids to `prepare()`. 500 integers are far below `max_allowed_packet` and the SQLite variable limit. Do not keep a cursor: each page selects from the top again, because the earlier rows are gone. Report `done` when the select returns fewer than 500. Build the `LIKE` pattern with `$wpdb->esc_like( 'User ID 12:' ) . '%'` and bind it as `%s`. Add an e2e check on SQLite that the eraser removes ID 12's rows and leaves ID 1's.
5. **Dedupe key: use `TransientStore` (the design is right), not `TableCounter`.** Dedupe does not need atomicity. A rare duplicate row when two requests race is harmless, and a miss costs only an extra row. Without an object cache, `get_transient()` is two primary-key lookups on `option_name` (timeout, then value) and one more per hit. That is about 0.1 ms each, and the value stays under the autoload limit because transients are not autoloaded. With an object cache it is one cache read and no SQL. `TableCounter` would cost four statements per call and add a purge duty. One caveat: expired transients in `wp_options` are only deleted when read or by WordPress's cleanup. One row pair per admin, range and method an hour is bounded by the admin set, and `uninstall.php` already removes `wpb_<md5>` rows.
